以下の手順で Conventional Commits 形式のコミットを作成してください。

1. `git status` でステージング状態を確認する
2. `git diff --staged` でステージ済み変更を分析する（空なら `git diff` も確認）
3. `git log --oneline -10` で既存のコミットスタイルを参照する
4. 変更内容から以下を判定する:
   - **type**: feat / fix / chore / docs / refactor / test / ci / build / perf のいずれか
   - **scope**: 変更されたディレクトリ名・モジュール名から推定（省略可）
   - **message**: 英語・現在形・50字以内
5. `git commit -m "type(scope): message"` を実行する

## ルール
- メッセージは英語・現在形（"add" ✓ / "added" ✗）
- Breaking change は `!` を付与: `feat!: ...`
- ステージされていないファイルがある場合はユーザーに確認する

## コミット粒度（重要）

複数の独立した変更（別々の指摘事項・別々の目的の変更）を1コミットにまとめない。目的が異なる変更（必須修正 vs 任意の改善、機能追加 vs バージョン固定、等）は別コミットに分ける。「レビュー指摘に対応」のような、変更の出どころだけを述べる抽象的なメッセージも避け、各コミットは単体のdiffを見ただけで意味が分かるように書く。

**検知シグナル**: コミットメッセージの本文を「1. 」「2. 」のような番号付き箇条書きで書きたくなった時点で、それは複数の変更をまとめてしまっている合図。番号を振らずに1段落で説明できないなら、複数コミットに分ける。レビューが複数の指摘を1コメント・1レビューにまとめて返してきた場合でも、指摘の数だけコミットを分けるのが既定動作。「提案する」だけでなく実際に分けてコミットする。

複数の独立修正が同じファイルの隣接行・同じdiffハンクに混ざっていても、それを理由にまとめない。すでにコミットしてしまった後でも、`git reset --soft`やHEAD時点のファイル（`git show HEAD:<file>`）を使って各修正だけを順に適用した中間版を作れば、後から分割し直せる。
