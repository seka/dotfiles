# PR の段階計画と stacked PR の管理

## 調査と境界の決定

- 関連する既存実装・呼び出し元・テストを調べ、再利用・拡張・新設の判断理由を整理する。代表的な実行経路を一つ追い、変更前後の依存関係とデータの流れを確認する。
- 要求を「変更する」「現状維持（理由）」「今回の対象外」に分け、完了条件を決める。
- 行数やファイル数ではなく、レビュアーが判断する責務と独立した検証単位で分割する。一つの責務の実装と振る舞いのテストはまとめる。
- 各段階は単独でビルド・テストでき、マージ後も有効な状態にする。契約変更と同時に直す必要のある実装はまとめ、実装・利用側移行・旧経路削除は独立して成立する場合に分ける。
- 未使用 API を先行させる場合は、具体的な利用目的、後続段階、受け入れ条件を明記する。将来使うかもしれない、だけの汎用 API は追加しない。

## 段階計画と実装

計画を作るときは [段階計画テンプレート](pr-staging-plan-template.md) を読み、必要な項目を使う。計画の保存先と PR の形式は対象リポジトリの規約に合わせ、個人用スキルの絶対パスをリポジトリ文書へ書き込まない。

各段階の目的、責務・範囲、前提 PR/base、依存が必要な理由、単独での検証方法を示す。段階境界を共有して合意してから、原則一段階ずつ実装する。既に合意された計画や継続の指示がある場合は、同じ確認を繰り返さない。

独立 PR は共通の開始ブランチから作り、依存 PR は先行 PR を base にする。開始ブランチ名はリポジトリで確認し、master/main を固定しない。PR 本文には前提 PR とマージ順を記載する。各段階の差分・必要な検証・CI の結果を確認してレビュー可能な状態を共有してから、依存する次段階へ進む。

## stacked PR の更新

1. 先行 PR のコミットを追加・修正・rebase したら、後続ブランチを依存順に更新する。変更前に作業ツリーと旧 base/head を確認し、未コミットの変更を巻き込まない。
2. 履歴とマージ方式に合わせて rebase 範囲を決める。先行が squash merge された場合などは、後続固有のコミットだけを新しい base へ移す必要がある。単純な rebase で先行の変更を再導入しないか確認する。
3. push は既存の許可とリポジトリ規約の範囲で行う。スキルの適用を push・履歴上書きの許可と解釈しない。許可がない場合もローカルの準備と検証は完了させ、残る操作を明示する。
4. 更新後は PR ごとに GitHub 上の base/head、先行 PR との差分、CI の対象 head と結果を確認する。実行中・未実行の CI を成功扱いせず、ローカルのみの結果と区別する。
5. 先行 PR のマージ後は、次の PR の base を対象の開始ブランチへ更新する。差分に先行 PR の変更が残っていないかと CI を再確認する。
6. PR 本文の変更内容・検証結果・制約・前提を最終差分に合わせて書き換える。base の変更だけで説明が変わらない場合は不要。

rebase で判断できない競合や他者の更新を見つけた場合は、履歴を書き換えて先へ進めず状況を共有する。
